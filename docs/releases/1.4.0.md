# Broke 1.4.0 — release notes

Published: **2026-10-29**. The annotated tag `v1.4.0` retains exact version
`1.4.0`; development continues as `1.4.1-dev` under the
[versioning policy](../../CONTRIBUTING.md#versioning-policy-option-b).
The [published release](https://github.com/777marvin/ext-broke/releases/tag/v1.4.0)
contains the signed archive, checksums and signature.

## Release notes

Broke 1.4.0 brings a simpler everyday badge, guided setup and a clearer account
of context savings. It also hardens indexing, history flushing, migration and
update ownership when operations are interrupted or incomplete.

### Highlights

- **Everyday controls and guided setup:** plain-language state, Safe / Balanced /
  Maximum savings choices, a live activity dot and a skippable setup guide.
  Advanced settings and diagnostics remain available.
- **Honest savings reporting:** the badge and `/broke stats` distinguish measured
  prompt reduction, provider-reported usage/cache activity and modeled cost
  estimates. Measured reduction does not prove a billed saving.
- **Output brevity and tool-output controls:** optional output directives,
  per-tool truncation overrides and opt-in tool-level truncation with
  secret-masked archives. See [tuning](../tuning.md) for the controls.
- **AiderDesk message-preparation support:** observe the pre-transform baseline
  and optionally anchor Anthropic prompt-cache control to a verified frozen
  prefix. Cache hits depend on the provider.
- **Safer interrupted operations:** retain usable index data after incomplete
  scans/reads, verify cached-summary coverage before partial flush, preserve full
  undo first, resume migrations without overwriting conflicts and serialize
  updater ownership outside the swappable installation.
- **Local summarizer privacy:** refuse Ollama HTTP redirects before forwarding
  a prompt or status request to another endpoint.

The complete change history is recorded in the [changelog](../../CHANGELOG.md).
Audit behavior and its limits are documented in
[audit verification](../audit-remediation.md).

### Compatibility and upgrade notes

- **Requires AiderDesk 0.88 or newer.** Upgrade hosts on 0.84–0.87 before
  installing this release; the required message-preparation hooks are absent
  there. The SDK dependency is `@aiderdesk/extensions` `^0.39.0`.
- **Requires Node.js 22 or newer** for development and dependency installation.
- Existing stored mode values `short`, `normal`, `long` and `custom` remain
  compatible with the new labels. Output brevity follows the presets: Safe
  disables it, Balanced uses `lite`, Maximum savings uses `full`. Manual
  overrides select Custom; `ultra` is an explicit custom choice.
- Partial `/broke flush` requires explicitly enabled undo storage and current,
  fingerprint-verified summary coverage. It preserves recent messages and never
  generates a summary implicitly. If coverage is stale, run
  `/broke summarize now` before retrying.
- Ambiguous updater ownership fails closed. Concurrent old/new updaters do not
  have a mixed-version guarantee; finish an in-progress update before retrying.
- Normal input compression leaves stored history unchanged. Explicit flush is
  the separate history-changing operation. Local model readiness does not
  establish cloud access, model quality or a monetary saving.

## Publication checklist

1. Review and merge the preparation changes through the normal protected-main
   process. Require green checks on the final preparation revision.
2. On the final release revision, set `package.json`, `package-lock.json` and
   `package-lock.json`'s root package entry to exact `1.4.0` (for example,
   `npm version 1.4.0 --no-git-tag-version --ignore-scripts`). Keep dependency
   resolutions unchanged. Move the current Unreleased entries to
   `## [1.4.0] - YYYY-MM-DD` using the actual publication date and retain an empty
   `## [Unreleased]` section. Update the README, overview, roadmap and these notes
   to reflect the intended release; do not claim publication before it succeeds.
3. Inspect the full diff and file list, then create the release commit and its
   annotated local tag `v1.4.0`. Check the tag does not already exist remotely
   before creating it. A tag must never point to the `-dev` preparation revision.
4. On that tagged revision, run all local gates from
   [Contributing](../../CONTRIBUTING.md#setup): version, docs, files, typecheck,
   tests, coverage and UI validation; also run `npm audit --audit-level=high`
   and `git diff --check`. Do not bypass failures or weaken the gates.
   `check:version` and the changelog tag check require the local release tag.
5. Inspect `git show v1.4.0:package.json`, verify the tag resolves to the release
   commit and confirm it is an ancestor of the final protected `main` revision.
   Inspect `git archive` contents so no local profiles, logs or working notes ship.
6. Push protected `main` first through the repository's authorized release
   process, then push **only** `v1.4.0`. Do not push every local tag. The branch
   CI may start before the tag exists and fail the version invariant; the full
   tagged CI gate is authoritative. See the
   [required push order](../../CONTRIBUTING.md#releasing).
7. Require the complete tagged CI gate to pass, then approve the existing
   `release` environment signing/publishing job. Do not manually publish an
   unsigned archive. Verify the resulting release contains
   `broke-v1.4.0.tar.gz`, `SHA256SUMS` and `SHA256SUMS.sig`. Use the release-notes
   section above for the public release body alongside the generated comparison.
8. Verify a signed update in an isolated AiderDesk profile. Existing real-host
   evidence covers headless integration and a separate browser fixture; a full
   interactive host GUI and non-expert usability evaluation remain separate.
9. After tagging, start `1.4.1-dev` in a separate commit, keeping both lockfile
   version fields synchronized. Update release-status prose to the verified
   publication result and rerun the version, docs and file gates.
